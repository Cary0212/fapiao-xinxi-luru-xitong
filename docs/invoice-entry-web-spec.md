# 发票信息录入与 Word 导出系统开发文档

版本：0.1（2026-10-23）  
状态：本机 Demo 已实现；下列完整产品需求仍保留作后续迭代依据  
项目目录：`D:\桌面\source-pdf`

## 1. 目标与范围

用户在浏览器中上传一份或多份已有发票、购物小票的 PDF。系统读取 PDF 中的票据信息，将识别结果呈现在可编辑表单中。用户核对并修正后，系统按项目内的报销模板生成一份可下载、可继续编辑的 `.docx` 文档。

首版以本项目的 5 份 PDF 为验收样本：`invoice1.pdf` 至 `invoice4.pdf` 为购物小票，`invoice5.pdf` 为出租车发票。输出模板为 `reference/invoice_template.docx`。模板字段与原件结构见 `invoice_template_spec.md`。

首版不承担发票真伪查验、税务合规判断、审批流或报销付款。系统只负责提取、核对、整理和填充文档。

## 2. 核心流程

```mermaid
flowchart LR
  A[上传 PDF] --> B[预览与页面处理]
  B --> C[文本提取或 OCR]
  C --> D[票据分类与字段提取]
  D --> E[人工核对和编辑]
  E --> F[校验与模板映射]
  F --> G[生成并下载 DOCX]
```

1. **上传**：支持一次选择一份或多份 PDF，并显示文件名、页数、处理状态和失败原因。保留原文件与每张票据的关联。
2. **预处理**：逐页判断是否有可用文字层。扫描页需做方向检测、旋转、有效票据区域裁切和清晰化，再进入中文 OCR。当前 5 份样本的 PDF 无可直接提取的正文文字，且票据在页面角落、方向不一致，不能只调用 PDF 文本提取接口。
3. **识别**：将每张票据分类为购物小票或出租车发票；提取字段、商品行和原文位置。未识别或有多个候选值的字段留待用户确认，不以猜测值直接生成 Word。
4. **核对**：页面同时显示 PDF 原图与可编辑字段。用户可更改票据类型、补充地址、修正金额、增删商品行，并标记该票据已核对。
5. **导出**：所有拟导出的票据核对完成后，填充 Word 模板，检查生成文件的字段、金额和排版，提供 `.docx` 下载。

## 3. 界面需求

### 3.1 上传与票据列表

- 上传区支持拖放和文件选择；仅接受 PDF。单个文件可以包含多页，不将“一个 PDF 等于一张票据”写死。
- 列表显示来源文件、页码、票据类型、日期、最终金额、识别状态、核对状态。
- 可以删除误传文件、重新识别失败文件，并识别同一批次中的重复文件或重复票号，提示用户决定是否保留。
- 顶部汇总显示购物小票数量及金额、出租车发票数量及金额、总金额。汇总随用户修改实时更新。

### 3.2 预览与编辑

- 左侧或主区域显示原 PDF 页，可缩放、旋转、定位到票据区域；右侧显示对应录入表单。
- 识别字段应显示“原文/候选值”和“当前确认值”；对低置信度、缺失或数值冲突的字段作明显提示。
- 购物小票表单包含商户名称、地址、日期、时间、票号或流水号、商品明细、原价合计、商家优惠、支付渠道优惠、最终应收或实付金额、支付方式和备注。
- 商品明细支持任意行数；每行至少含名称、单价、数量、单位和小计。重量商品允许小数数量。
- 出租车发票表单包含开具方、发票代码、发票号码、日期、金额；车号、上下车时间、里程和备注作为可选记录。
- 用户可手动新增票据，作为 OCR 无法识别时的补救路径。

### 3.3 导出前检查

- 必需的模板字段为空时，指出具体票据和字段；不能静默填入空白或零。
- 号码始终按文本处理，保留前导零和超过 15 位的长号码。
- 金额统一以人民币元保存，两位小数展示。原价、商家优惠、支付渠道优惠、最终金额分别保存；发现算术不一致时提示核对，不自动覆盖票面金额。
- 购物小票的票号/流水号不能标成税务发票号码。出租车发票代码与发票号码分别保存。
- 导出前显示将进入 Word 的票据顺序与字段摘要，用户可调整顺序。

## 4. 数据模型

| 实体 | 关键字段 | 关系与说明 |
| --- | --- | --- |
| 报销批次 `batch` | ID、创建时间、状态、最终合计 | 一次上传与导出操作对应一个批次。 |
| 来源文档 `source_document` | ID、批次 ID、文件名、文件哈希、页数、存储位置 | 一份 PDF 可关联多张票据；哈希用于重复上传提醒。 |
| 票据 `receipt` | ID、来源文档 ID、页码、类型、商户/开具方、地址、日期、时间、号码、号码类型、发票代码、原价、商家优惠、支付渠道优惠、最终金额、支付方式、核对状态、备注 | 金额使用十进制定点数；号码使用字符串。 |
| 商品 `line_item` | ID、票据 ID、序号、名称、单价、数量、单位、小计 | 仅购物小票使用；一张小票可有任意数量商品行。 |
| 识别证据 `extraction_evidence` | 票据 ID、字段名、OCR 原文、页码、区域坐标、置信度 | 用于在 PDF 预览中定位、复核；人工修改不覆盖原始识别记录。 |

建议保存 `extracted_value` 与 `confirmed_value` 两套值，并记录修改时间。导出只读取已确认值。首版可使用本地数据库与文件目录保存批次；若后续需要多人协作，再补用户与权限模型。

## 5. 识别与金额规则

- 优先读取 PDF 文字层；没有可用文字时走 OCR。中文、数字、小数点、日期、票号都需要专项校验。
- 分类先依据票据版式、关键词和印章信息给出建议，用户可以改选。类型改变时仅切换适用字段，不删除已识别原文。
- 日期规范化为 `YYYY-MM-DD`，保留票面时间原值；遇到不完整或模糊日期时等待核对。
- `line_item` 的小计可根据单价与数量给出参考值，但票面最终金额是独立字段。商家优惠可解释商品合计与应收之间的差额；支付渠道优惠另记，不自动从小票应收中扣减。
- 同一文件哈希或同一类型加号码重复时提示“可能重复”，由用户确认；仅凭金额或商户相同不自动合并。
- OCR 失败、票据边缘裁切、金额冲突和无法识别的商品行都应保持可编辑状态，并在列表中显示待处理原因。

## 6. Word 模板映射与输出规则

| Word 模板位置 | 数据来源 |
| --- | --- |
| 购物小票 `地址 / Address` | `receipt.address`，不以商户名替代地址。 |
| 购物小票 `日期 / Date` | `receipt.date`。 |
| 购物小票 `合计金额 / Total Amount (¥)` | `receipt.final_amount`。 |
| 商品表的名称、单价 | 按 `line_item.position` 排序逐行写入。 |
| 出租车 `发票号码 / Invoice No.` | `receipt.number`，保留原始字符串。 |
| 出租车 `日期 / Date` 与 `金额 / Amount (¥)` | `receipt.date` 与 `receipt.final_amount`。 |

现有模板固定为 4 张购物小票和 1 张出租车发票，每张小票只有 3 个商品行。生成器必须能增加商品行；超出 4 张小票或 1 张出租车发票时，按相同样式追加票据块并自然分页。若后续要求 Word 与原模板页数完全一致，需要另定溢出规则，不能截断数据。未用到的模板票据块应删除或不显示，而不是留下空表。

生成的文档保留原模板的中英文字段标签与标题。导出文件名建议为 `发票信息汇总_YYYYMMDD_HHMM.docx`。系统生成前后需核对票据数量、号码、日期、金额、商品行数量和合计金额，并渲染 Word 检查表格没有溢出、错页或文字遮挡。源 PDF 和确认后的数据不写入生成文档的隐藏元数据。

## 7. 实现方案建议

- **前端**：浏览器单页应用，负责批量上传、PDF 预览、字段编辑、状态提示和下载。组件应把票据列表、原件预览、编辑表单分开，方便后续调整布局。
- **后端**：提供上传、识别、保存修改、校验、导出接口；异步处理较慢的 OCR 任务，前端轮询或订阅状态。
- **PDF/OCR**：以独立适配层封装文字提取、渲染、方向与区域处理、中文 OCR。先用 5 份样本评估识别效果，再确定具体 OCR 引擎与部署方式；不能假设运行环境已安装中文语言包。
- **DOCX**：以 `reference/invoice_template.docx` 为母版，按字段定位并填充表格；新增行或票据块时复制相应样式。不要把最终 Word 当作截图或图片输出。
- **存储**：首版以本地文件加轻量数据库实现，可离线运行；文件路径由服务端生成，上传文件名只作显示，避免覆盖已有文件。

建议接口：`POST /api/batches` 创建批次，`POST /api/batches/{id}/documents` 上传，`GET /api/batches/{id}` 查询状态与票据，`PATCH /api/receipts/{id}` 保存确认值，`POST /api/batches/{id}/validate` 校验，`POST /api/batches/{id}/export-docx` 生成 Word。具体技术框架可在实施时根据运行环境确定。

## 8. 验收标准

1. 上传本项目 5 份 PDF，系统能显示 5 张票据并将前 4 张归为购物小票、第 5 张归为出租车发票；分类有误时可手动改正。
2. 五张票据的最终金额经核对分别为 **7.90、12.30、19.42、31.80、44.00 元**，合计 **115.42 元**。
3. `invoice2.pdf` 的 4 件商品可完整录入和导出，不受模板原有 3 行限制；小票应收保留 **12.30 元**，另印的支付宝支付优惠 **0.08 元**单独记录。
4. `invoice4.pdf` 记录原价 **43.80 元**、商家优惠 **12.00 元**、应收 **31.80 元**，导出使用应收金额。
5. `invoice5.pdf` 的发票号码 **26117535** 与发票代码 **131002360715** 保持文本原样；Word 模板按要求填入发票号码、日期、金额。
6. 用户可在界面修正任一识别字段并保存；重新打开批次后修正值仍在，导出采用修正值。
7. 下载的 `.docx` 可由 Word 打开并继续编辑；所有 5 张票据均出现，无商品行截断、空白占位票据或金额错位。
8. 对损坏 PDF、无有效票据页、OCR 失败和缺少关键金额分别给出可理解的错误或待核对提示，不生成看似完整但数据缺失的 Word。

## 9. 实施顺序

1. 建立上传、批次和票据数据模型；完成 PDF 原图预览。
2. 接入文字提取与 OCR，针对 5 份样本建立字段提取与分类规则。
3. 做可编辑核对界面、明细行增删、金额校验和批次汇总。
4. 实现模板填充、动态扩行与追加票据块，完成 DOCX 导出和视觉回归检查。
5. 以第 8 节样本验收，并保留后续新增票据版式的 OCR 适配接口。

## 10. 实施前需确认的产品选择

- 首版是只在本机使用，还是部署为局域网/公网多人系统；这决定登录、权限和文件保留策略。
- 是否必须逐页复刻当前 Word 模板的排版，还是允许为超额商品和票据自然续页。本方案按自然续页设计。
- 是否需要在导出的 Word 中额外显示商户名称、票号、折扣、支付方式及总汇总；当前模板没有这些位置，本方案先保存数据但不擅自加入模板。

## 11. 当前 Demo 实施记录

已实现：多份 PDF 上传、逐页文字读取或本地 OCR、票据分类与字段提取、旋转裁切后的原件预览、可编辑表单、商品行增删、批次金额汇总、保存核对结果、基于现有模板导出一份 DOCX。界面无需登录；数据保存在本机 `web_demo/data/jobs/`。

以本机 5 份 PDF 验证：识别 4 张购物小票和 1 张出租车发票，金额合计 115.42 元；第二张小票的 4 行商品、第四张小票的优惠和出租车发票号码均保留。Word 样例位于本机 `output/demo_invoice_summary.docx`，已用 Word 渲染检查分页。原始 PDF 与已填写的 Word/Excel 不随公开仓库发布。

为控制 Demo 范围，以下完整产品功能暂未实现：误传文件删除与重识别、重复票据检测、OCR 区域坐标定位、单独的候选值比较、手动新建票据、明细小计与金额冲突提示、拖动调整导出顺序、独立的导出前摘要页。现有导出接口会检查日期、最终金额、购物商品行和出租车发票号码；`已核对` 标记供人工记录，不作为 Demo 的强制导出条件。OCR 误读仍需对照原件人工修正。
